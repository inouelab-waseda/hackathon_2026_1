# API 通信規約（フロント ⇄ バックエンド）

割り勘アプリのフロントエンド（React）とバックエンド（Flask）の間の取り決め。
**バックエンド（`backend/domain/calculate.py`）の実装内容に合わせて確定済み**です。
フロント側（`frontend/src/api/warikanApi.ts`）もこの仕様で実装・接続確認が済んでいます。

---

## 0. 全体のルール

| 項目 | 取り決め |
|---|---|
| リクエスト／レスポンス形式 | JSON |
| **キーの命名** | **camelCase**（`totalAmount` など）。Python 的には snake_case が自然ですが、変換層を挟むとバグの温床になるためフロントの型に合わせています |
| 学年のキー | `"M2"` / `"M1"` / `"B4"` / `"B3"` の4つ。**常に4つすべてを含める**（人数0の学年も省略しない） |
| 金額の型 | 整数（円）。小数は使わない |
| 文字コード | UTF-8 |
| CORS | 開発時は Vite の proxy 経由で同一オリジンに見えるため**設定不要**です |

---

## 1. 割り勘の計算

### `POST /api/calculate`

3パターンの傾斜で計算した案を返します。

#### リクエスト

```json
{
  "totalAmount": 48000,
  "counts":       { "M2": 3,    "M1": 4,    "B4": 5,    "B3": 2 },
  "fixed":        { "M2": false, "M1": false, "B4": false, "B3": false },
  "fixedAmounts": { "M2": 5000, "M1": 4000, "B4": 3000, "B3": 2500 }
}
```

| フィールド | 意味 |
|---|---|
| `totalAmount` | 支払いたい合計金額 |
| `counts` | 学年ごとの人数 |
| `fixed` | 金額をあらかじめ固定した学年。`true` の学年は傾斜配分の対象外 |
| `fixedAmounts` | 固定した場合の1人あたり金額。**`fixed` が `false` の学年の値は無視してください**（画面上の入力値が残っているだけです） |

#### 成功レスポンス（200）

**ボディは Plan の配列そのもの**（オブジェクトで包まない）。

```json
[
  {
    "id": "steep",
    "name": "案A",
    "perPerson": { "M2": 5000, "M1": 3500, "B4": 3000, "B3": 2000 },
    "surplus": 0
  },
  { "id": "standard", "name": "案B", "perPerson": { ... }, "surplus": 0 },
  { "id": "flat",     "name": "案C", "perPerson": { ... }, "surplus": 0 }
]
```

| フィールド | 意味 |
|---|---|
| `id` | 案を識別する文字列。**同じ案には常に同じ値**を使ってください（画面のリスト描画に使います） |
| `name` | 画面に表示する名前。**「案A」「案B」「案C」**。アプリ側で性格づけ（「上級生を厚めに」等）はしない方針です |
| `perPerson` | 学年ごとの1人あたり負担額 |
| `surplus` | 余剰金額（徴収合計 − 支払い金額） |

#### エラーレスポンス

| ステータス | `error` | 意味 |
|---|---|---|
| 400 | `validation_failed` | 入力が不正（人数・金額・固定指定など） |
| 422 | `calculation_failed` | 入力は妥当だが計算できなかった |

```json
{ "error": "validation_failed", "errors": ["合計金額を入力してください。"] }
```

`errors` は**そのまま画面に表示する日本語の文字列**の配列です。フロントは `errors` だけを読み、`error`（種別）は現在使っていません。ステータスコードによらず同じ形で扱えるようにしてあります。

## 2. バックエンドが満たすべき条件（実装済み・変更時は維持してください）

**フロントの画面が壊れないために必要な条件**です。現在の実装はすべて満たしていることを確認済みです。計算方法を変更する際も、この5点は維持してください。

1. **`surplus` は必ず 0 以上。**
   負の値（＝徴収額が支払い金額に足りない）は「幹事の持ち出し」を意味し、仕様上ありえません。

2. **`perPerson` には4学年すべてのキーを含める。**
   人数が0の学年も `0` を入れてください（キーが無いとフロント側でエラーになります）。

3. **案は必ず3件、`steep` → `standard` → `flat` の順。**
   配列の順序がそのまま画面の表示順（案A → 案B → 案C）になります。

4. **固定した学年の `perPerson` は、リクエストの `fixedAmounts` の値をそのまま返す。**
   固定額に丸めや調整をかけないでください。

5. **同じ入力には常に同じ結果を返す**（ランダム要素を入れない）。

### バリデーションの分担

正しさの保証はサーバ側の責任です。フロントの検証は「無駄な往復を減らし、反応を速くするため」のもので、フロントを通過した入力でもサーバ側で必ず再検証してください。

| チェック内容 | フロント | バックエンド |
|---|---|---|
| 合計金額が0以下 | ✓ | ✓ |
| 総人数が0 | ✓ | ✓ |
| 全学年を固定（配分先が無い） | ✓ | ✓ |
| 型が不正（数値でない・真偽値でない等） | — | ✓ |
| **固定額の合計が支払額を超える** | — | ✓ |

**固定額の合計が支払額を超えるケースはバックエンドだけが弾いています。** フロントは通過させ、返ってきた 400 のメッセージをそのまま画面に出します。動作としては正しいので、このままにしています。

## 3. 傾斜係数はバックエンドが持ちます

**3案の傾斜係数（目標比）はバックエンドの管理とします。** 計算の一部であり、2箇所に置くと必ず片方だけ修正されてずれるためです。

係数の実体は `backend/domain/constants.py` の `WEIGHT_PRESETS` にあります。フロント側に係数は持っていません（接続時に削除しました）。**係数を調整したい場合はバックエンド側を変更してください。**

現在の値は次のとおりです（B3 = 1.00 とした相対値）。**プロトタイプ由来の暫定値で、チーム合意はまだです。**

| 案 | M2 | M1 | B4 | B3 |
|---|---|---|---|---|
| 案A (`steep`) | 2.08 | 1.68 | 1.21 | 1.00 |
| 案B (`standard`) | 1.60 | 1.40 | 1.10 | 1.00 |
| 案C (`flat`) | 1.12 | 1.12 | 0.99 | 1.00 |

## 4. 接続状況

**接続済みです。** フロントは計算をすべてバックエンドに依頼しており、フロント側にあった暫定計算（`domain/calculate.ts`・傾斜係数・丸め単位）は削除しました。二重実装は残っていません。

手元での確認は次のコマンドでできます。

```bash
curl -X POST http://localhost:5001/api/calculate \
  -H 'Content-Type: application/json' \
  -d '{"totalAmount":48000,
       "counts":{"M2":3,"M1":4,"B4":5,"B3":2},
       "fixed":{"M2":false,"M1":false,"B4":false,"B3":false},
       "fixedAmounts":{"M2":0,"M1":0,"B4":0,"B3":0}}'
```

## 5. 決済履歴（接続済み）

確定した割り勘をSQLiteへ保存し、履歴画面へ新しい順で返します。`id`と`savedAt`はバックエンドが発行します。

| エンドポイント | 用途 |
|---|---|
| `POST /api/settlements` | 確定した割り勘を1件保存する |
| `GET /api/settlements` | 保存済みの決済を新しい順に返す |

### `POST /api/settlements`

#### リクエスト

```json
{
  "eventName": "歓迎会",
  "shopName": "研究室食堂",
  "totalAmount": 49000,
  "counts": { "M2": 3, "M1": 4, "B4": 5, "B3": 2 },
  "perPerson": { "M2": 5000, "M1": 4000, "B4": 2500, "B3": 2500 },
  "surplus": -500,
  "hasPayerContribution": true,
  "payerContributionAmount": 500
}
```

| フィールド | 意味 |
|---|---|
| `eventName` / `shopName` | 任意入力。空文字列は`null`として保存 |
| `counts` / `perPerson` | 4学年すべてを含む人数と1人あたり金額 |
| `surplus` | 徴収合計 − 支払い金額。手動調整後に不足する場合は負 |
| `hasPayerContribution` | `surplus < 0`なら`true` |
| `payerContributionAmount` | `surplus < 0`なら`-surplus`、それ以外は0 |

成功時は、バックエンドが発行した`id`と`savedAt`を加えた`SettlementRecord`を201で返します。入力値同士が整合しない場合は400と`validation_failed`を返します。

### `GET /api/settlements`

保存済みの`SettlementRecord`配列を新しい順に200で返します。履歴がない場合は`[]`です。

SQLiteの実体はComposeの`backend_data` named volumeに保存します。旧スキーマが見つかった場合は、既存履歴を保持したまま立て替え対応スキーマへ自動移行します。
