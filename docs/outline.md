# 研究室割り勘アプリ — 全体方針 (outline)

> 本ドキュメントは「何を作るか / どう分担するか」の**全体方針のみ**を定義する。
> 詳細仕様（画面ワイヤー、API スキーマ、係数の最終値など）は別ファイル（`docs/` 配下）に切り出す。
> 記号: ✅ = 合意済みとして進める / ❓ = 要チーム決定

---

## 1. プロダクト概要

研究室の飲み会・イベントで、**学年（B3〜M2）ごとに負担額へ傾斜をつけて割り勘する**Webアプリ。

- 「上級生が多めに払う」という研究室の暗黙ルールを、その場で・揉めずに・数秒で数値化することが価値。
- 幹事がスマホでその場で使うことを想定。**入力2項目 → 3案提示 → 選ぶだけ**が最短動線。

### 対象学年
`B3` / `B4` / `M1` / `M2` の4区分。✅
（教員・D・OB は MVP のスコープ外。将来「特別枠」として拡張余地を残す）

---

## 2. スコープ定義

### MVP（ハッカソン当日に必ず動かす）
| 区分 | 内容 |
|---|---|
| 入力（必須） | ① 各学年の人数（4つ） ② 割る合計金額 |
| 出力（必須） | 傾斜の異なる **3パターン**の割り勘案。各案について「学年ごとの1人あたり金額」「学年ごとの小計」「合計」「端数（過不足）」を表示 |
| 動作 | フロントエンドのみで完結（オフラインでも計算可能） |

### オプション（MVP後、時間が余れば）
- **固定額指定**: 1つの学年だけ「1人あたり◯円」を固定し、残額を他学年で傾斜配分する。✅（優先度: 最高のオプション）
- 結果のシェア（テキストコピー / URL共有）
- 丸め単位の切り替え（10円 / 100円 / 500円）

### 将来案（ハッカソン後、バックエンド前提）
- **端数貯金**: 割り勘で生じた端数（切り上げによる余剰）を毎回サーバに記録して累積し、一定額に達したら**先生への誕生日プレゼント代**に充てる。
- 履歴の保存・参照、研究室単位のアカウント。
- 重い計算（最適化ベースの配分探索など）はバックエンドに委譲する。

## 3. 計算方針

### 3.1 基本モデル
学年 $g$ の重み係数を $w_g$、人数を $n_g$、総額を $T$ とする。

```
基準単価 base = T / Σ(n_g × w_g)
学年gの1人あたり = round(base × w_g,  丸め単位)
```

- 丸め単位: **100円**（デフォルト）✅ / 切り上げ方向を基本とする ❓
- 丸めによって「徴収合計 ≥ T」となるようにし、**差額（端数）は必ず正または0**にする。
  → この端数が将来の「端数貯金」の原資になる、という設計上の一貫性を持たせる。
- 端数の扱い（MVP）: 徴収せず**表示するだけ**（「余り ◯◯円」）。誰が持つかは人間が決める。

### 3.2 3パターンの傾斜（係数案）❓最終値は要決定
| パターン | 呼称 | B3 | B4 | M1 | M2 | 想定シーン |
|---|---|---|---|---|---|---|
| A | ゆるやか | 1.0 | 1.1 | 1.2 | 1.3 | 学年差を出しすぎたくない日常の飲み会 |
| B | 標準 | 1.0 | 1.2 | 1.5 | 1.8 | 歓迎会・追いコンなど標準的な会 |
| C | 上級生厚め | 1.0 | 1.5 | 2.0 | 2.5 | 新入生歓迎・学部生に配慮したい会 |

- 係数は**コード内に定数として集約**し、後から差し替え・追加が容易な形にする。
- 「B3の負担額」を基準（1.0）に固定して考えると議論しやすい。

### 3.3 固定額指定（オプション機能）
1学年 $f$ の1人あたりを $p_f$ に固定する場合:

```
残額 T' = T - n_f × p_f
残りの学年について T' を通常どおり傾斜配分
```

- **バリデーション必須**: `T' < 0` になる指定（固定額が高すぎ）、固定学年以外の人数が0、などは計算前に弾いてエラー表示。

### 3.4 エッジケース（実装前に合意しておく）
- 総人数0 / 金額0 / 負値 → 入力バリデーションで弾く
- 人数が0の学年 → 出力から除外（0円行を出さない）
- 1学年しかいない → 単純割り勘にフォールバック

## 4. 技術方針

### 4.1 構成（MVP）
- **フロントエンドのみ**。SPA として完結させ、バックエンドなしでデプロイする。
- 推奨スタック ❓: **TypeScript + React + Vite**（ハッカソンでの立ち上がりの速さとメンバーの習熟度を優先）
- スタイル ❓: Tailwind CSS など、CSS設計で消耗しないものを選ぶ
- デプロイ ❓: Vercel / GitHub Pages のいずれか（当日中に URL が出せることを重視）

### 4.2 ビルド・実行環境は Docker に統一する ✅

> **開発・ビルド・実行はすべて Docker 上で行う。ホストに Node.js を直接入れる前提を置かない。**

- 理由: 6人が別々のマシン（Mac / Windows / WSL）で作業するため、**「自分の環境では動く」を最初から潰す**ことが最大の時短になる。Node のバージョン差による事故はハッカソンで最も頻発する。
- 参加者に要求するのは **Docker と git だけ**。`docker compose up` 一発で開発サーバが立ち上がる状態をゴールとする。

#### 想定するファイル構成
```
Dockerfile              … マルチステージ（development / build / production）
compose.yml             … 開発用サービス定義（ソースをバインドマウント + HMR）
.dockerignore           … node_modules, .git, docs などを除外
```

#### 方針の要点
| 項目 | 方針 |
|---|---|
| ベースイメージ | `node:22-alpine`（バージョンはここで一元管理し、全員がこれに従う）❓ |
| 開発 | ソースをバインドマウントし、コンテナ内で dev サーバを起動。**HMR が効くこと**を必須要件とする |
| `node_modules` | ホストと共有しない（named volume に逃がす）。OS 差によるネイティブモジュールの破損を防ぐ |
| 本番ビルド | マルチステージで build → 成果物のみを軽量イメージ（nginx など）にコピー ❓ |
| コマンド | `npm` を直接叩かせず、`docker compose run` 経由に揃える。手順は README に1箇所だけ書く |

- **注意点**: バインドマウント + HMR は Mac/Windows でファイル監視が効かないことがある。効かない場合は polling を有効化する（担当6が初日に全員のマシンで動作確認する）。
- デプロイ先が Vercel / GitHub Pages の場合はプラットフォーム側でビルドされるため Docker は使われないが、**ローカルの開発体験を揃えることが主目的**なので方針は変えない。将来バックエンドを足す際にそのまま compose にサービスを追加できる利点もある。

### 4.3 最重要のアーキテクチャ原則
> **計算ロジックを UI から完全に分離する。**

- 割り勘計算は純粋関数（入力 → 出力、副作用なし）としてドメイン層に隔離する。
- 理由: ① 将来バックエンドへ移すときにそのまま移植できる ② UI 担当と計算担当が並行作業できる ③ 単体テストが書ける（ハッカソンでもここだけはテストを書く価値がある）

```
src/
  domain/     … 計算ロジック（純粋関数・係数定義）※テスト対象
  ui/         … 画面
  types/      … 入出力の型定義（フロント/バックの契約になる）
```

### 4.4 将来のバックエンド（端数貯金フェーズ）
- **入出力の型を最初から「API のリクエスト/レスポンス相当」の形で定義しておく**。こうしておくと、バックエンド化は「関数呼び出しを fetch に置き換える」だけになる。
- 想定: 計算 API + 端数の累積を保持するストレージ。技術選定はフェーズ2で改めて行う ❓
- 「重い計算はバックエンドに任せる」方針は上記の分離により後付けで成立する。
- バックエンドと DB は `compose.yml` にサービスとして追加する形にする（4.2 の方針がそのまま活きる）。

## 5. チーム分担（6人）

計算ロジックと UI を疎結合にすることで、**初日から6人が同時に着手できる**状態を作る。

| # | 役割 | 担当範囲 |
|---|---|---|
| 1 | **設計 / 取りまとめ** | 型定義・係数定義の確定、リポジトリ初期構築、PR レビュー、進行管理 |
| 2 | **計算ロジック（コア）** | 基本の3パターン計算、丸め・端数処理の純粋関数 |
| 3 | **計算ロジック（拡張・テスト）** | 固定額指定モード、バリデーション、単体テスト |
| 4 | **UI: 入力画面** | 人数入力・金額入力・オプション入力のフォーム、入力体験（スマホ前提） |
| 5 | **UI: 出力画面** | 3案の比較表示、内訳、端数表示、シェア機能 |
| 6 | **インフラ / 品質 / デモ** | **Docker 環境（Dockerfile / compose.yml）の整備**、デプロイ環境、CI、READMEとデモシナリオ、発表資料 |

- 2と3、4と5はそれぞれペアで密に連携する。1が両者の**インターフェース（型）を最初に確定**させることが全体のボトルネック解消になる。
- 手が空いた人はオプション機能（3.3、将来案の下ごしらえ）に合流する。

### 進め方
0. **着手前**: 担当6が Docker 環境の雛形を用意し、**全員が `docker compose up` で同じ画面を見られる**ことを確認する（ここが揃わないと並行作業が成立しない）
1. **最初の30分**: 型定義（入力型・出力型）と係数テーブルを1で確定 → 全員に共有
2. 以降は各自ブランチを切って並行開発、`main` へ PR
3. 早い段階で「動く最小の状態」を作り、デプロイまで一度通す（デモが出せない事故を防ぐ）
