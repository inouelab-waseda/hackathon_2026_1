# 研究室割り勘アプリ — 全体方針 (outline)

> 本ドキュメントは「何を作るか / どう分担するか」の**全体方針のみ**を定義する。
> 詳細仕様（画面ワイヤー、API スキーマ、係数の最終値など）は別ファイル（`docs/` 配下）に切り出す。
> 記号: ✅ = 決定済み / ❓ = 要チーム決定

---

## 1. プロダクト概要

研究室の飲み会・イベントで、**学年（B3〜M2）ごとに負担額へ傾斜をつけて割り勘する**Webアプリ。

- 「上級生が多めに払う」という研究室の暗黙ルールを、その場で・揉めずに・数秒で数値化することが価値。
- 幹事がスマホでその場で使うことを想定。**入力2項目 → 3案提示 → 選ぶだけ**が最短動線。
- さらに、割り勘のたびに出る端数を貯めて**先生への誕生日プレゼント代**にする、という研究室ならではの仕掛けを組み込む。

### 対象学年
`B3` / `B4` / `M1` / `M2` の4区分。✅
（教員・D・OB は当面スコープ外。将来「特別枠」として拡張余地を残す）

---

## 2. スコープ定義

本プロジェクトは2フェーズで進める。**フェーズ2までの完成をハッカソンの最終ゴールとする。** ✅

### フェーズ1: 割り勘計算（フロントエンドのみで完結）
まず「動いて価値が出る最小形」をここで確定させる。デモが出せない事故を防ぐため、最優先で仕上げる。

| 区分 | 内容 |
|---|---|
| 入力（必須） | ① 各学年の人数（4つ） ② 割る合計金額 |
| 出力（必須） | 傾斜の異なる **3パターン**の割り勘案。各案について「学年ごとの1人あたり金額」「学年ごとの小計」「合計」「端数（過不足）」を表示 |
| 動作 | ブラウザ内で計算が完結し、バックエンドなしで動く |

**オプション（フェーズ1の余力で）**
- **固定額指定**: 1つの学年だけ「1人あたり◯円」を固定し、残額を他学年で傾斜配分する。✅（優先度: 最高）
- 結果のシェア（テキストコピー / URL共有）
- 丸め単位の切り替え（10円 / 100円 / 500円）

### フェーズ2: 端数貯金（バックエンド + DB）★ 最終ゴール
- **端数貯金**: 割り勘で生じた端数（切り上げによる余剰）をサーバに記録して累積し、一定額に達したら**先生への誕生日プレゼント代**に充てる。
- 貯金額の現在値・履歴を画面で確認できる（「あと ◯◯円でプレゼント」のような進捗表示）。
- 割り勘の実行履歴を保存・参照できる。
- **計算ロジックをバックエンドへ移す**。重い計算（最適化ベースの配分探索など）もここに載せられる状態にする。

### 将来案（ハッカソン後）
- 研究室単位のアカウント / 認証
- 教員・D・OB を含めた学年区分の一般化
- プレゼント代の使途記録

## 3. 計算方針

### 3.1 基本モデル
学年 $g$ の重み係数を $w_g$、人数を $n_g$、総額を $T$ とする。

```
基準単価 base = T / Σ(n_g × w_g)
学年gの1人あたり = round(base × w_g,  丸め単位)
```

- 丸め単位: **100円**（デフォルト）✅ / 切り上げ方向を基本とする ❓
- 丸めによって「徴収合計 ≥ T」となるようにし、**差額（端数）は必ず正または0**にする。
  → この端数がそのままフェーズ2の「端数貯金」の原資になる。**フェーズ1と最終ゴールを貫く設計の背骨**なので、ここは崩さない。
- 端数の扱い:
  - フェーズ1 … 徴収せず**表示するだけ**（「余り ◯◯円」）
  - フェーズ2 … 同じ値をサーバに記録し、累積する

### 3.2 3パターンの傾斜（係数案）❓最終値は要決定
| パターン | 呼称 | B3 | B4 | M1 | M2 | 想定シーン |
|---|---|---|---|---|---|---|
| A | ゆるやか | 1.0 | 1.1 | 1.2 | 1.3 | 学年差を出しすぎたくない日常の飲み会 |
| B | 標準 | 1.0 | 1.2 | 1.5 | 1.8 | 歓迎会・追いコンなど標準的な会 |
| C | 上級生厚め | 1.0 | 1.5 | 2.0 | 2.5 | 新入生歓迎・学部生に配慮したい会 |

- 係数は**1箇所の定数として集約**し、後から差し替え・追加が容易な形にする。
- 「B3の負担額」を基準（1.0）に固定して考えると議論しやすい。

### 3.3 固定額指定（オプション機能）
1学年 $f$ の1人あたりを $p_f$ に固定する場合:

```
残額 T' = T - n_f × p_f
残りの学年について T' を通常どおり傾斜配分
```

- **バリデーション必須**: `T' < 0` になる指定（固定額が高すぎ）、固定学年以外の人数が0、などは計算前に弾いてエラー表示。

### 3.4 エッジケース（実装前に合意しておく）
- 総人数0 / 金額0 / 負値 → 入力バリデーションで弾く
- 人数が0の学年 → 出力から除外（0円行を出さない）
- 1学年しかいない → 単純割り勘にフォールバック

## 4. 技術方針

### 4.1 技術スタック ✅（先輩と協議のうえ決定）

| レイヤ | 採用 | 理由 |
|---|---|---|
| フロントエンド | **TypeScript + React + Vite** | 立ち上がりが速く、メンバーの習熟度が高い |
| バックエンド | **Python + Flask** | 書きやすさ最優先。エンドポイント数が少ないので軽量フレームワークで十分 |
| データベース | **SQLite** ❓ | ファイル1つで完結し、セットアップ不要。規模的にこれで足りる |
| スタイル | Tailwind CSS など ❓ | CSS設計で消耗しないものを選ぶ |
| 実行環境 | **Docker / docker compose** | 4.2 参照 |
| デプロイ先 | ❓ | バックエンドを含むため静的ホスティング単体では不可。要検討（4.5） |

- **SQLite の注意点**: ファイルベースなので、コンテナを作り直すとデータが消える。**必ず named volume（またはホストのマウント）に置く**こと。ここを忘れると「デモ中に貯金額が消える」事故になる。
- 言語がフロント（TS）とバック（Python）で分かれるため、**両者の境界＝API の形を早期に固める**ことが最重要（4.3）。

### 4.2 ビルド・実行環境は Docker に統一する ✅

> **開発・ビルド・実行はすべて Docker 上で行う。ホストに Node.js / Python を直接入れる前提を置かない。**

- 理由: 6人が別々のマシン（Mac / Windows / WSL）で作業するため、**「自分の環境では動く」を最初から潰す**ことが最大の時短になる。とくに今回は TS と Python の2言語構成なので、環境差の事故確率がさらに上がる。
- 参加者に要求するのは **Docker と git だけ**。`docker compose up` 一発でフロントもバックも立ち上がる状態をゴールとする。

#### 想定するファイル構成
```
compose.yml             … frontend / backend のサービス定義
frontend/
  Dockerfile            … マルチステージ（development / build / production）
  .dockerignore
backend/
  Dockerfile
  .dockerignore
docs/                   … 本ドキュメントなど
data/                   … SQLite のファイル置き場（gitignore 対象、volume でマウント）
```

#### 方針の要点
| 項目 | 方針 |
|---|---|
| ベースイメージ | フロント `node:22-alpine` / バック `python:3.12-slim`（バージョンはここで一元管理し、全員がこれに従う）❓ |
| 開発 | ソースをバインドマウントし、コンテナ内で dev サーバを起動。**フロントの HMR とバックの自動リロードが効くこと**を必須要件とする |
| `node_modules` | ホストと共有しない（named volume に逃がす）。OS 差によるネイティブモジュールの破損を防ぐ |
| Python 依存 | `requirements.txt` で固定。イメージビルド時にインストールする |
| SQLite | named volume に置き、コンテナ再作成でデータが消えないようにする |
| 本番ビルド | フロントはマルチステージで build → 成果物のみを軽量イメージ（nginx など）に配置 ❓ |
| コマンド | `npm` / `pip` を直接叩かせず、`docker compose run` 経由に揃える。手順は README に1箇所だけ書く |

- **注意点**: バインドマウント + HMR は Mac/Windows でファイル監視が効かないことがある。効かない場合は polling を有効化する（担当6が初日に全員のマシンで動作確認する）。
- フロントからバックへのアクセスは、開発時は Vite の proxy 設定で同一オリジンに見せると CORS 対応が不要になり楽。❓

### 4.3 最重要のアーキテクチャ原則

> **計算ロジックを UI から完全に分離し、その境界を最初から「API の形」で定義する。**

- 割り勘計算は**純粋関数**（入力 → 出力、副作用なし）としてドメイン層に隔離する。
- 入出力の型は、**そのまま HTTP のリクエスト/レスポンスになる形**で定義する。こうしておくと、フェーズ2 の移行が「関数呼び出しを `fetch` に差し替えるだけ」で済む。
- 理由: ① フェーズ1→2 の移行コストがほぼゼロになる ② UI 担当と計算担当が並行作業できる ③ 単体テストが書ける（ハッカソンでもここだけはテストを書く価値がある）

```
frontend/src/
  domain/     … 計算ロジック（純粋関数・係数定義）※テスト対象
  ui/         … 画面
  types/      … 入出力の型定義（= フロント/バックの契約）
backend/
  app.py      … Flask のエントリポイント
  domain/     … 計算ロジック（Pythonへの移植先）
  db/         … SQLite アクセス
```

#### 計算を「どちらに置くか」問題 ✅方針を決めておく
TS と Python の両方に計算ロジックがあると、**必ず片方だけ直されて挙動がズレる**。これを避けるため、次のルールを守る。

1. フェーズ1 … 計算は **TypeScript 側のみ**に存在する
2. フェーズ2 … 計算を **Python 側へ移植**し、**移植が済んだ時点で TS 側の計算ロジックは削除**する（フロントは API を叩いて表示するだけになる）
3. 二重実装を「保険」として残さない。残した瞬間に破綻する

- 移植の正しさを担保するため、**同じテストケース（入力→期待出力）を TS と Python で共有できる形（JSON など）で持っておく**とよい。移植時にそのまま回帰テストになる。

### 4.4 バックエンド設計の方針（フェーズ2）

- **エンドポイントは最小限に保つ**。増やすほど並行作業の調整コストが上がる。想定は次の3つ程度 ❓
  - 割り勘計算（入力を受け取り3パターンを返す）
  - 端数の記録（確定した割り勘の端数を積む）
  - 貯金状況の取得（現在の累積額・目標額・履歴）
- **DB スキーマも最小限に**。「割り勘の実行記録」1テーブル ＋ 必要なら「設定（目標額など）」1テーブルで足りる ❓
- 認証は入れない（研究室内利用・ハッカソンのスコープ）。✅
- **端数の記録は「ユーザーが確定操作をしたときだけ」行う**。計算するたびに勝手に積むと、試算しただけで貯金が増えてしまう。

### 4.5 デプロイ ❓
- バックエンドがあるため、GitHub Pages のような静的ホスティング単体では成立しない。
- 候補: ①コンテナをそのまま動かせる PaaS（Render / Fly.io / Railway など） ②研究室のマシン・VPS で `docker compose up`
- **フェーズ1の時点で一度デプロイまで通しておく**こと。最後にまとめてやると必ず間に合わない。

## 5. チーム分担（6人）

計算ロジックと UI を疎結合にすることで、**初日から6人が同時に着手できる**状態を作る。
フェーズ1とフェーズ2で担当がシフトする前提で組む。

| # | 役割 | フェーズ1 | フェーズ2 |
|---|---|---|---|
| 1 | **設計 / 取りまとめ** | 型定義・係数定義の確定、リポジトリ初期構築、PR レビュー、進行管理 | API スキーマの確定、フロント/バックの結線の統括 |
| 2 | **計算ロジック（コア）** | TS で3パターン計算・丸め・端数処理の純粋関数 | 計算ロジックの Python 移植 |
| 3 | **計算ロジック（拡張・テスト）** | 固定額指定、バリデーション、単体テスト | 共有テストケースで移植の等価性を検証 |
| 4 | **UI: 入力画面** | 人数・金額・オプションのフォーム（スマホ前提） | 確定操作（端数を貯金に積む）の導線 |
| 5 | **UI: 出力画面** | 3案の比較表示、内訳、端数表示、シェア | 貯金状況・履歴の画面 |
| 6 | **インフラ / 品質 / デモ** | Docker 環境（compose / 各 Dockerfile）、CI、README、デモシナリオ | Flask + SQLite の基盤構築、デプロイ、発表資料 |

- 2と3、4と5はそれぞれペアで密に連携する。1が両者の**インターフェース（型 / API スキーマ）を最初に確定**させることが全体のボトルネック解消になる。
- 6はフェーズ1の Docker 環境が固まり次第、早めにフェーズ2のバックエンド基盤に着手してよい（フェーズ2が最終ゴールなので、ここが最長経路になりやすい）。
- 手が空いた人はオプション機能やフェーズ2の下ごしらえに合流する。

### 進め方
0. **着手前**: 担当6が Docker 環境の雛形を用意し、**全員が `docker compose up` で同じ画面を見られる**ことを確認する（ここが揃わないと並行作業が成立しない）
1. **最初の30分**: 型定義（入力型・出力型）と係数テーブルを1で確定 → 全員に共有
2. 以降は各自ブランチを切って並行開発、`main` へ PR
3. **フェーズ1を早期に完成させ、デプロイまで一度通す**（デモが出せない事故を防ぐ）
4. フェーズ1が固まってからフェーズ2に全体を寄せる。フェーズ1が終わらないうちにフェーズ2へ人を割きすぎない

## 6. 成功基準
